# Plan: migrate the plugin documentation website to Astro Starlight

## Context / goal

Replace the current custom Astro website with a clean-slate Astro Starlight site using the default theme. Help developers find plugin documentation, guides, changelogs, and npm packages while preserving existing human-facing URLs.

This is the approved migration plan. Implementation details and validation were refined during implementation as recorded below. All implementation changes must remain inside `docs-website/`. Plugin packages remain read-only content sources.

## Agreed requirements

- Start from the standard Starlight setup on the latest stable Astro version available at implementation time, with compatible Starlight and Node versions.
- Use Starlight's default theme, fonts, light/dark mode, navigation, table of contents, code styling, and built-in search (Pagefind). Do not recreate the existing custom design.
- Existing website code may be removed once its routes and required content have been migrated. Prefer documented built-in features over custom plugins, theme overrides, or routing workarounds.
- Keep plugin README files, changelogs, and package metadata in `../packages/` as the source of truth. Do not edit or maintain copies in plugin packages.
- Add a clearly labeled npm link on each plugin documentation page, using the full package name from its `package.json`: `https://www.npmjs.com/package/{package-name}`. Preserve scoped package names.
- Preserve all existing human-facing routes, plugin slugs, guide slugs, and inbound heading anchors. Do not substitute redirects to a new URL structure.
- Include Starlight's built-in search and verify that it indexes plugin documentation, changelogs, and guides in the production build.
- Do not migrate `llms.txt` or the `/llms/` Markdown endpoints. These machine-readable routes are explicitly excluded from URL preservation.

## Route contract

| Content              | Required public route                |
| -------------------- | ------------------------------------ |
| Homepage             | `/`                                  |
| Plugin documentation | `/plugin/{existing-slug}/`           |
| Plugin changelog     | `/plugin/{existing-slug}/changelog/` |
| Guides overview      | `/guides/`                           |
| Guide                | `/guides/{existing-slug}/`           |
| AI integration page  | `/ai-integration/`                   |

Preserve public assets referenced by migrated content and continue serving a real 404 page. Retain the existing site origin, `https://plugins.pinelab.studio`, and trailing-slash canonical URLs seen in the current sitemap.

## Implementation steps

### 1. Capture the baseline

- Capture the live sitemap and compare it with locally generated routes to identify any differences before replacing the site.
- Record human-facing paths, internal links, heading anchors, and referenced assets as the migration verification baseline.
- Inventory current plugin discovery rules, metadata, guide content, and deployment settings. Preserve the current plugin slug derivation from package names, not directory names.

### 2. Establish a clean Starlight foundation

- Replace the custom Astro setup with the official Starlight starter structure inside `docs-website/`; do not scaffold over the repository root.
- Install the latest stable Astro and compatible Starlight dependencies, check their runtime requirements against deployment, and keep the docs-specific manifest and lockfile local.
- Configure the existing site origin and explicit trailing-slash behavior. Use standard Starlight defaults rather than carrying over custom CSS, fonts, React, or Tailwind configuration.
- Keep deployment changes within `docs-website/`, including its Netlify configuration. If a required change would affect root workspace files or external CI configuration, stop and request approval rather than expanding scope.

### 3. Migrate content and routes

- Use the standard docs collection for guides and straightforward content pages. Set explicit slugs where needed to retain the route contract; existing guide frontmatter slugs must become full `guides/{existing-slug}` paths.
- Use the default splash template and built-in components for the homepage, with links to plugins and guides. Preserve useful homepage fragment targets such as `#plugins`.
- Generate disposable Markdown inputs at the preserved `plugin/{slug}` and `plugin/{slug}/changelog` paths before starting Astro. These generated files are gitignored, never maintained by hand, and always refreshed from package sources. Use the standard `docsLoader()` and `docsSchema()` rather than custom pages, a custom loader, or a Starlight plugin.
- Render package Markdown with Starlight's standard pipeline, including its default code highlighting, heading links, and table of contents. Verify historical anchor IDs.
- Use Starlight's built-in autogenerated sidebar with plugin and guide groups. Hide changelog entries from the sidebar while keeping them linked from plugin pages and indexed by search.
- Include plugin title, description, install command, npm package link, and a changelog link. Keep useful version and compatibility information without recreating bespoke badges or layouts.
- Retain guide and AI integration content, descriptions, canonical URLs, and useful structured metadata using supported Astro/Starlight facilities. Remove links advertising the retired LLM endpoints.

### 4. Verify search and remove legacy code

- Enable Starlight's default Pagefind search, including production indexing of custom plugin/changelog pages. Validate this in a built preview, not only the development server.
- Remove obsolete pages, layouts, components, styles, dependencies, and LLM endpoint generators once replacements are verified.
- Retain required public assets and sitemap generation without duplicate integrations or sitemap entries for retired LLM endpoints.
- Keep a static deployment using the standard Astro build output; do not add a server adapter unless a demonstrated requirement emerges.

### 5. Validate and prepare the implementation PR

Run all build and verification commands from `docs-website/`. Compare the migrated production build against the baseline and review the scoped diff before committing.

## Definition of done

- The latest stable Astro and compatible Starlight build successfully with the documented deployment runtime.
- All agreed human-facing URLs render their corresponding content directly, with the default Starlight presentation. No plugin package or file outside `docs-website/` changes.
- Every plugin documentation page links to its correct npm package and changelog.
- Starlight search finds plugin documentation, changelogs, and guides and opens the correct result URLs.
- No LLM endpoint generation or navigation links remain. This is an intentional exclusion, not a failed route-preservation check.
- Validation (updated by the developer: no test suite is required; run the production build and smoke-check `dist` against the live website):
  - **Build and ad-hoc smoke checks:** clean production build succeeds; baseline live sitemap paths have generated output; representative headings and all same-origin internal links resolve; npm links match package metadata, including scoped names; sitemap URLs preserve the route contract and exclude retired LLM routes. No permanent test runner or test suite is added.
  - **Manual in production preview:** homepage, plugins overview links, representative plugin and changelog pages, guides overview and guide pages, and AI integration page render correctly; old bookmarked headings land on the expected section.
  - **Manual search:** a plugin name, a phrase unique to a changelog, and a guide title return relevant results at the preserved URLs; a nonsense query shows the default no-results state.
  - **Manual usability:** mobile navigation and search are usable; light/dark modes, code blocks, long tables, external npm links, and the 404 page behave correctly.
  - **Scope:** the final diff contains changes only under `docs-website/`.
- The implementation PR description must remain at 200 words or fewer and include:
  - User-facing bullet points explaining what changed and why.
  - A simple execution-flow pseudocode diagram with arrows/branches and at most 10 short steps.
  - Numbered reviewer validation steps with expected results, plus screenshots where useful.

## Expected execution flow

Package docs + guide Markdown → load content and metadata → preserve slugs → render default Starlight pages → generate sitemap and Pagefind index → deploy static output → browse or search → open existing documentation URLs / npm packages.
