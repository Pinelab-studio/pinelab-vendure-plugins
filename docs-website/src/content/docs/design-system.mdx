This is a styling workbench, not a public documentation guide. Each section places real Starlight components beside ordinary headings and paragraphs so you can judge spacing, contrast, and rhythm in context. Resize the window to review mobile layouts and use keyboard navigation to inspect focus states. The current site hides its theme picker; to compare theme variables, change the `<html>` element's `data-theme` attribute between `light` and `dark` in browser developer tools.

The page covers every component family in the [Starlight component reference](https://starlight.astro.build/components/using-components/). It inherits `src/styles/pinelab.css` without adding its own theme overrides. It is excluded from navigation, site search, and the sitemap, and asks search engines not to index it. It is still publicly accessible by URL; this is not access control.

## Typography

Good documentation starts with a clear title and a short explanation. This paragraph contains **strong emphasis**, *subtle emphasis*, an [ordinary documentation link](/guides/), and inline code such as `npm install`. Compare their weight, color, and line height before adjusting the surrounding components.

### A section within a guide

A longer paragraph helps reveal the reading measure. When a merchant adds a plugin to a Vendure store, the documentation should make the next step obvious while leaving enough room for details, examples, and practical advice. Links should remain recognizable without competing with the main call to action.

#### Supporting details

- Keep installation instructions close to the configuration example.
- Explain important defaults and provide links for further reading.
- Use components to support the content, not replace it.

> Prefer a small, well-understood configuration over unnecessary customization. This blockquote shows how supporting advice sits alongside normal prose.

<details>
<summary>Expandable supporting information</summary>

This is a native disclosure, useful for optional explanations. Its summary, focus state, and expanded spacing should remain comfortable in both themes.

</details>

## Asides

Asides call attention to information without interrupting the reader's place in a guide. These examples cover the default note, every semantic type, a custom title, and a custom icon. [Component reference](https://starlight.astro.build/components/asides/).

<Aside>

The default note is useful for background information. Read the [installation guide](/guides/) before changing your configuration.

</Aside>

<Aside type="tip">

Keep a local copy of your configuration so you can try a plugin without affecting the production store.

</Aside>

<Aside type="caution">

Check your Vendure version before installing a new plugin release. A breaking release may require a database migration.

</Aside>

<Aside type="danger">

Never run destructive database commands against production without a verified backup and a rollback plan.

</Aside>

<Aside type="note" title="Before you begin">

Custom titles should remain readable when they wrap onto a second line on a narrow screen. You will need access to the store's configuration and deployment process.

</Aside>

<Aside type="tip" title="Ready for launch" icon="rocket">

A custom icon can reinforce the message while retaining the standard semantic color and layout.

</Aside>

## Cards

Cards highlight a feature or a useful piece of information. A plain card and an icon card show the two basic treatments before we place them in a grid. [Component reference](https://starlight.astro.build/components/cards/).

<Card title="A focused feature">

A card without an icon relies on typography and spacing. It can contain **emphasis**, `inline code`, and a [link to related guides](/guides/).

</Card>

<Card title="Documentation that grows with your store" icon="open-book">

An icon gives the title a visual anchor. Longer content should wrap without crowding the title or reaching the edge of the card.

</Card>

## Code

Code should be as easy to read as the surrounding explanation. These examples exercise the `Code` component and the same Expressive Code features used by Markdown fences: editor, terminal, and frameless treatments; marked, inserted, and deleted lines; word highlighting; wrapping; and raw file imports. [Component reference](https://starlight.astro.build/components/code/).

### Editor frame and line markers

In this illustrative configuration, the highlighted line identifies the setting to review. Inserted and deleted lines show how a change can be communicated without relying on prose alone.

### Terminal frame

A command should feel distinct from application code, with a recognizable terminal frame and a working copy control.

## Steps

Steps give a procedure a clear sequence. The component has no props; its useful variations come from the content inside each step. This example mixes a short instruction with a code block, a nested list, and an aside. [Component reference](https://starlight.astro.build/components/steps/).

<Steps>

1. **Open the documentation project.**

   Work from `docs-website/` so the build uses the correct package and content sources.

2. **Build a production preview.**

   ```sh
   corepack yarn build
   corepack yarn preview
   ```

3. **Review the result in context.**

   - Compare light and dark themes.
   - Check a narrow mobile viewport.
   - Follow links and try keyboard navigation.

   <Aside type="tip">Keep this page open while adjusting the shared stylesheet so you can compare component families together.</Aside>

</Steps>

## Tabs

Tabs group alternative instructions in the same space. Compare ordinary labels, labels with icons, and synchronized groups. Use the arrow keys while a tab is focused to check keyboard navigation. [Component reference](https://starlight.astro.build/components/tabs/).

### Plain tabs

A basic pair works well for short explanations that should not appear simultaneously.

<Tabs>
  <TabItem label="Development">

    Run the development server while editing prose or styles. Content updates are reflected without a production deployment.

  </TabItem>
  <TabItem label="Production">

    Build the static website before reviewing the generated search index and deployment output.

  </TabItem>
</Tabs>

### Tabs with icons

Icons add a visual cue while the text label remains the accessible description of the panel.

<Tabs>


  </TabItem>
  <TabItem label="Deployment" icon="server">

    Build the documentation and publish the generated `dist/` directory to the hosting provider.

  </TabItem>
</Tabs>
